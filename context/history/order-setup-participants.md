## Session Notes

- Implemented on `task/order-setup-participants` off the post-Favorites `main`. Web order mocks are fully removed: Home, Orders, and the order detail page render real Neon-backed data. Mobile ordering, receipts, notifications, and Stage 2 voting/food-picks UI remain out of scope per the ordering design decisions.
- Decisions carried forward from the spec (`docs/superpowers/specs/2026-08-17-ordering-design.md`): deadline-driven state transitions are a lazy `advanceOrder` seam that stays a no-op until Stage 2; the shortlist lives in `order_shortlist_restaurants`; voting-disabled orders pin the fallback selection at creation; `restaurant_deadline` is set to creation time when voting is off so the food-after-voting invariant stays meaningful.
- Authorization boundary: the service is authoritative. Plain members cannot create orders, participants must be active group members, and only the order's creating manager or a group owner can cancel. The detail page hides the cancel button via `viewer.canManage`, and a non-participant opening an order URL gets the not-found page (avoids leaking order existence).
