# V1-07 Group details, creation, and persistent invites

Subtasks:

- Group details, creation, and persistent invites design and implementation plan
- Persistent `group_invite_links` table (`0004_secret_nextwave.sql`) with partial unique index enforcing one active link per group
- Group name validation and persistent invite-link mint/hash/prefix helpers in `packages/domain`
- Strict parsers for group details, rename, create, rotate-link, and accept-link requests/responses in `packages/contracts`
- `requireGroupMembership`, `requireGroupRole`, and `requirePlatformAdmin` authorization helpers isolated for the upcoming Effective permissions refactor
- DB repositories for group details read, active-link lookup by hash, and link rotation
- Web use cases for load details, rename, rotate-link, and admin create-group
- Next.js API routes for `GET /api/groups/:groupId/details`, `POST /api/groups/:groupId/rename`, `POST /api/groups/:groupId/invite-link/rotate`, and `POST /api/admin/groups/create`
- Invitation acceptance updated to honor the persistent-link path; the legacy single-use `invitations` table is preserved read-only
- Web member Groups list and `GroupDetails` page with inline rename, copy link, and rotate-link controls
- Web admin Groups page with real rows and a Create-group dialog (name + owner picker)
- Mobile Groups list with real names and a tap target that opens the new Group details screen
- Mobile `GroupDetailsScreen` presentational component with name, viewer role label, owner, and member roster
- Documentation updates to `progress-tracker.md`, `architecture.md`, and `project-structure.md`

## Session Notes

- Implemented on `task/V1-07-group-details-creation-and-invites` off the reviewed V1-06 + Multi-group foundation `main`. The visible Group membership journey is now in place on web and Android; the invitation model is one persistent multi-use link per group; Platform Admins can create groups from the web admin portal.
- `packages/db/drizzle/0004_secret_nextwave.sql` introduces `group_invite_links` with `id`, `group_id`, `token_hash`, `token_prefix`, `created_by_user_id`, `created_at`, `rotated_at`, and `status`. A `status_values` check constrains status to `active` or `rotated`; a `rotated_fields_match` check requires `rotated_at` to be `null` iff status is `active`. The partial unique index `group_invite_links_one_active_per_group` enforces one active link per group. Existing single-use `invitations` rows are preserved read-only; the public acceptance route no longer honors them.
- Domain adds `validateGroupName` with a 60-character cap, the `GroupDetails`/`GroupOwnerSummary`/`GroupMemberSummary`/`GroupInviteLinkSummary` read-model types, the `GROUP_DETAIL_ROLES` enum, and `mintInviteLink`/`hashPublicValue` helpers. The raw public value is never stored; only its sha256 hash and a short non-secret prefix are persisted.
- Contracts add strict parsers for the group details response, the rename request, the create-group request, the rotate-link response, and the accept-link request. The mobile and web clients use the same `parseGroupDetailsResponse` so the read path has one boundary.
- The route handlers run through the existing seven-step discipline and use small authorization helpers (`requireGroupMembership`, `requireGroupRole`, `requirePlatformAdmin`) that the Effective permissions foundation bundle can replace without touching callers or UI. The simple role checks in these helpers are deliberate scope; they will be refactored by that bundle.
- Invitation acceptance looks up the active link by hash, verifies deployment binding, and creates or reactivates exactly one membership per user per group without consuming the link. Repeat acceptances by the same already-active user return the existing safe `CONFLICT` without writing a duplicate audit event. Rotated links and any old single-use tokens presented after this bundle ship both fall through to the same safe `CONFLICT` response.
- The web member `GroupDetails` page (`apps/web/app/(member)/groups/[groupId]/page.tsx` with `apps/web/app/components/group-details-view.tsx`) renders the name, role, owner, member roster, and an owner-only invite-link section with inline rename, copy, and rotate controls. The web admin Groups page (`apps/web/app/admin/groups/page.tsx` with `apps/web/app/components/create-group-dialog.tsx`) renders real rows and a Create-group dialog with a name and an owner picker populated server-side from active product users.
- The mobile Groups list (`apps/mobile/app/(member)/groups.tsx` with `MobileMemberAccessState`) renders real membership IDs and roles and routes a tap to the new `apps/mobile/app/(member)/groups/[groupId].tsx`. The new route fetches `GET /api/groups/:groupId/details` using `buildAuthenticatedRequestInit`, manages loading / forbidden / error / ready states with retry, and renders the read-only `GroupDetailsScreen` (`apps/mobile/src/features/groups/group-details-screen.tsx`). Rename, copy, and rotate-link actions are web-only in this round and are deferred on mobile until the Effective permissions bundle lands.
