# V1-22 Session receipt attachments

Implemented on October 6, 2026, on the task branch. Development migration applied; final browser upload acceptance is waiting on development R2 CORS. Production migration/deployment remain separate.

## Behavior

- Per-session owner switch defaults off, with Group/Individual mode and explicitly selected submitters. Owner submits when enabled; Managers need selection. Multiple JPEG/PNG/WebP/PDF receipts up to 10 MiB contain a positive PHP amount and optional 2,000-character note.
- Group receipts are shared with session participants. Individual receipts are self-only; current Owners and Managers audit all. Selected participants submit/edit/remove their own uploads. Owner manages all and assigns Individual receipts to any current participant. Removing participants preserves audit receipts without preserving their access.
- Disabling prevents writes but preserves viewing. Mode changes affect new uploads; prior receipts keep their visibility. Revoking permission prevents upload finalization and later edits/removal. Existing single-receipt rows migrate as Group receipts with an unknown legacy amount. Receipt amounts do not modify food subtotals.
- Private R2 uses five-minute uploads signed for content type, server-side type/size/signature checks, conditional copying of the inspected object to a separate final key, and one-minute authorized read URLs. No public bucket or public image optimizer. Upload finalization is idempotent and cannot resurrect a removed receipt.
- Database-backed cleanup queues receipt/session/group files transactionally. Pending upload intents expire after ten minutes; cleanup removes orphaned pending/final copies, preserving attached final files. Failed deletions retry. Receipt requests drain bounded work and a daily Vercel callback uses CRON_SECRET; absent credentials fail closed.

## Remaining acceptance

The configured development R2 bucket rejects browser preflight for http://localhost:3001 (403, no allowed origin). The configured Object Read & Write key can handle files but cannot read/manage bucket CORS. Cloudflare CORS must allow the local app origins and PUT/GET/HEAD with content-type before the live browser upload can be accepted. Configuration is documented in context/services/service-setup.md. Production additionally needs its own bucket/origin, CRON_SECRET and migration before deployment. Separate-user browser role acceptance and native Android were not performed.
